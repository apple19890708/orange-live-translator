# 與 jt-live-whisper 的技術比較

> 日期：2026-11-23　｜　對象：[jasoncheng7115/jt-live-whisper](https://github.com/jasoncheng7115/jt-live-whisper)（v2.34.1，Apache-2.0，606 星）
> 重點：**辨識說話內容**與**翻譯**兩個層面。依 [CLAUDE.md](../CLAUDE.md) 規則，能量測的都用同一份參考稿實測後才決定是否採用。

## 1. 兩個專案的定位

| | jt-live-whisper | Orange Live Translate（本專案） |
|---|---|---|
| 主要場景 | 會議、課程、簡報（中英為主，另有台語） | 日文 VTuber／直播（日文為主，英文為輔） |
| 平台 | macOS、Windows、Linux | Windows |
| 聲音 | 系統聲音（＋麥克風） | **指定的 Chrome 分頁**（或系統聲音） |
| 辨識 | whisper.cpp、faster-whisper（large-v3-turbo 預設）、mlx、Breeze-ASR-26（台語）、Qwen3-ASR（實驗） | faster-whisper large-v3、anime-whisper（可切換） |
| 翻譯 | Ollama／OpenAI 相容（gemma4:26b 預設）、NLLB、Argos | Ollama：Sakura 7B（日文）、qwen3:8b（英文） |
| 額外功能 | 說話者分辨、錄音後高精度處理、摘要、關鍵字提醒、遠端 GPU 伺服器、WebUI | YouTube 字幕翻譯、字幕疊在影片上、字幕紀錄 |

## 2. 他們的技術 × 我們的實測

參考稿：白玖ウタノ歌枠公告 7 分 40 秒，`scripts/eval_asr.py`；目前設定 CER **7.2%**。

### 2.1 辨識

| 技術 | 他們的做法 | 我們的實測 | 決定 |
|---|---|---|---|
| 溫度階梯 | 0.0→1.0 六段重試 | 7.2%（沒變），辨識慢 18% | 不採用，維持 0／0.2／0.4 |
| `compression_ratio_threshold 2.4`、`log_prob_threshold -1.0` | 明確設定 | 和 faster-whisper 預設相同，結果一樣 | 改成明確設定（`asr.*` 可調） |
| `repetition_penalty 1.05` | 有用 | 6.6%，但逐字比對：修好「13万」，卻把「大石まさよし」聽成「雅也」，還**整句漏掉「よろしくお願いします」**（直播常重複的話被懲罰） | 不採用，保留成選項 |
| 音量正規化（太小聲時放大到 -18 dBFS） | 錄音檔處理 | 7.4%（變差）；YouTube 聲音本來就正規化過 | 不採用，保留成選項 |
| 降噪（noisereduce） | 即時可開 | 未測：歌枠背景音樂是持續性的，固定式降噪會傷人聲 | 暫不採用 |
| 主題注入（會議主題） | 放進翻譯提示詞 | 把直播標題放進 Whisper 提示詞：7.5～7.8%（變差） | 不採用 |
| 提示詞（hotwords） | **刻意不用**：他們實測會議中出現無關人名幻聽 | 我們實測有用：關掉 9.0%、開著 6.8%；但沒有前文時會冒出「スタッフ スタッフ」 | 維持使用；詞彙表要只放直播會出現的詞 |
| LLM 校正辨識結果 | 錄音後處理，中文 CER 13.85%→12.35% | qwen3:8b：7.2%→7.2%，只刪了逗號，沒修到任何真錯字（本機 8B 模型日文能力不夠；他們用 27B） | 不採用（腳本保留：`scripts/eval_correction.py`） |
| Qwen3-ASR | 中文大幅改善（28.78%→15.75%） | 他們自己把日文排除（長檔結果較差） | 不適用 |
| 卡住片段過濾 | 30 秒以上只有幾個字的片段丟掉 | 我們句子最長 12 秒，不會發生 | 不需要 |
| 依標點切句 | Qwen 結果依「。？！」切 | 已有（`segmenter.py`、長句找句號切） | 已具備 |

### 2.2 翻譯

| 技術 | 他們的做法 | 我們 | 決定 |
|---|---|---|---|
| 繁體保護清單 | s2twp 會把繁體輸入轉壞（干擾→幹擾），轉完還原 | 實測確認我們也會：qwen3 常直接輸出繁體，「干擾、干預」被轉成「幹擾、幹預」 | **採用**：轉換後修正「幹擾／幹預／幹涉」；並統一「臺→台」（台灣字幕慣用） |
| 前文 | 前 5 組原文／譯文 | 前 4 組 | 差異小，不改 |
| 只放相關詞彙 | 詞彙最多 80 個並檢查相關性 | 已有（只放這句出現的詞） | 已具備 |
| 台灣用語規則寫進提示詞 | 「必須使用繁體中文」、軟體／記憶體… | 提示詞要求台灣用語＋OpenCC s2twp | 已具備 |
| 關閉思考模式 | `think=False` | 已有 | 已具備 |
| 雲端／大模型翻譯 | gemma4:26b | 顯示記憶體放不下（規則：預設 ≤10GB） | 不採用 |

## 3. 值得之後考慮的功能（未實作）

1. **直播結束後的高精度重轉**：我們已經有每場錄音（`logs/*.pcm`）。可以在直播後用 Whisper 的離線模式（整段 30 秒視窗、前後文完整）重新辨識、翻譯，產出更準的字幕檔。之前實測離線模式能聽對「台北から」「ライブイン台北」這類即時模式聽錯的句子。
2. **說話者分辨**：連動、雜談多人時可以標出誰在說話；單人直播用不到。
3. **關鍵字提醒**：聽到指定詞（例：主播名字、「メン限」）時跳通知。

## 4. 結論

- 他們的辨識調校（解碼參數、正規化、主題、LLM 校正）在我們的日文直播資料上**都沒有帶來實質改善**。原因是場景不同：他們針對會議錄音與中文，我們是背景音樂多、口語化的日文直播，而且我們已經做過一輪針對性調整。
- 實際採用的是**繁體轉換保護**（已實作並測試）。
- 最有潛力的下一步是第 3 節的「直播後高精度重轉」，可直接利用現有錄音。
